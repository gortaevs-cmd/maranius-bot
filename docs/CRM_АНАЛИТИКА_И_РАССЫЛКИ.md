# CRM, аналитика и рассылки Maranius

```yaml
status: proposed
created: 2026-08-26
owner: Maranius
decision: PostgreSQL — единый источник правды; Twenty — CRM-интерфейс и рабочее место менеджера; n8n — оркестратор интеграций.
```

## Цель

Собрать единую, проверяемую историю отношений с клиентом: от первого запуска бота до покупки, выдачи VIP, обучения и повторной коммуникации. Сегментация и отправка сообщений должны опираться не на редактирование JSON/CSV вручную, а на сохранённые правила, согласия и журнал кампании.

Важные понятия не смешиваются:

| Понятие | Значение | Источник факта |
|---|---|---|
| `VIP-доступ` | доступ к разделу «🔑 Моё VIP» (колоды, материалы); **не равен покупке** | `users.json`: `vip = true` / в целевой схеме — `access_grants` |
| `VIP-клиент` | совершил оплаченную покупку продукта, открывающего VIP | подтверждённый `order` / платёж |
| `подписчик рассылки` | отдельно выразил согласие на маркетинговые сообщения в конкретном канале | неизменяемый `consent_log` |
| `доступный получатель` | подписчик, который не заблокировал бот и не находится в стоп-листе | расчёт перед конкретной отправкой |

Поэтому ручная выдача доступа или тестовый seed-аккаунт не превращают человека в VIP-клиента. Это предотвращает неверную аналитику выручки и повторных продаж.

### Термин «VIP» в текущем боте

В коде и CSV-сегментах слово **VIP** означает **VIP-доступ** — право открыть раздел «🔑 Моё VIP». Это не статус «купил продукт» и не признак подписчика рассылки.

Покупка в будущем будет фиксироваться отдельно (`orders` / `VIP-клиент`). До миграции сегмент «VIP» в `/god → Списки` строится по флагу `vip` в `users.json`, без проверки оплаты.

## Что уже фиксируется

### Пользователь и доступ

`users.json` в runtime хранит Telegram ID, `@username`, имя, язык, Premium-статус, первый и последний визит, геолокацию/часовой пояс при добровольной отправке локации, ежедневную практику, текущий VIP и источник выдачи, статус блокировки бота, внутренний признак и согласия.

Отдельно `platform_users.json` содержит кросс-сервисный профиль: UUID, email, телефон, Telegram ID, имя, источники и произвольные metadata. Курсы пишутся в `user_courses.json`.

В локальном историческом файле встречается `zenclass_user_id`, хотя текущий `DATA_REGISTRY.md` уже не описывает Zenclass-поля. Перед миграцией нужно сверить происхождение этого поля и сохранить его как identity типа `zenclass`, а не потерять при очистке схемы.

### VIP-доступ: как выдаётся сейчас (реализовано)

**Что открывает доступ:** флаг `vip = true` в `users.json` → пользователь видит меню колод и материалов в «🔑 Моё VIP». Без флага бот просит VIP-код.

**Поля в `users.json`:** `vip`, `vip_granted_at`, `vip_source`, при снятии — `vip_revoked_at`.

**Источники выдачи (`vip_source`):**

| Источник | Как выдаётся | Кто может |
|---|---|---|
| `code` | Пользователь вводит код в «🔑 Моё VIP»; код из `data/vip/codes.json` (active → used) | Любой пользователь с валидным кодом |
| `admin_grant` | Команда в режиме бога или кнопка «✅ Открыть доступ» на алерте о неверном коде | Только seed-admin (`SEED_ADMIN_IDS`, сейчас `186758977`) |
| `import` | Массовый импорт telegram_id | Только seed-admin |
| `seed_admin` | Автоматически при старте бота для аккаунтов из `SEED_ADMIN_IDS` | Система |

**Ручная выдача администратором — четыре способа:**

1. **`/god → VIP → 👑 Импорт VIP`** — список `telegram_id` (по строке) или CSV с id в первой колонке. Новым ставится `vip_source = import`; уже VIP пропускаются.
2. **`/god → Пользователи`** — текстовые команды с подтверждением: `vip 123456789` / `grant_vip 123456789` — выдать; `unvip 123456789` / `revoke_vip 123456789` — снять (`vip_revoked_at`). Поддерживается numeric id; `@username` — только если пользователь уже есть в `users.json`.
3. **Алерт о неверном коде** — админу приходит сообщение с кнопками «✅ Открыть доступ» / «❌ Отклонить»; approve → `admin_grant`, пользователю уходит уведомление о доступе.
4. **`/god → VIP → ➕ Добавить коды`** — добавляет коды в пул (`data/vip/codes.json`); пользователь активирует сам (`code`). Это не прямая выдача доступа, а пополнение кодов.

**Управление кодами:** `/god → VIP → 🔑 Сводка кодов` (active/used), **📎 Выгрузка кодов** — CSV `vip_codes.csv`.

**Доступ к админке:** `/god` и все VIP-операции — **только seed-admin** (`SEED_ADMIN_IDS`). Файл `admins.json` используется для других функций (группы/каналы), но guard режима бога проверяет seed-id.

**Важно для аналитики и рассылок:** ручная выдача и импорт создают **VIP-доступ**, но не создают **VIP-клиента** (покупку). Seed-аккаунты помечаются `is_internal = true` и исключаются из «чистой» статистики и рассылок.

### Поведение и обратная связь

- `activity_events.json`: `{ts, user_id, section}` для переходов по разделам (90 дней, максимум 50 000 событий);
- `activity_aggregates.json`: недельные и месячные сводки;
- `inbox.json`: неизвестные команды/ангельские знаки, попытки повторного VIP-кода и прочие отклонения сценария (90 дней);
- `events.json`: подписки, отписки и реакции в группах/каналах;
- VIP-коды (`data/vip/codes.json`): активный/использованный код, Telegram ID и время активации.

В `/god → Списки` уже можно выгрузить CSV: подписанные/отписавшиеся, с согласиями/без них, давшие согласие на маркетинг, VIP, активные 7/30 дней, спящие и стоп-лист. Есть недельный и месячный отчёт администратору.

### Что пока отсутствует

Нет связанной с платёжной системой сущности заказа и оплаты, единого ID клиента во всех источниках, истории изменения профиля/согласий, товарной аналитики, журнала рассылок и фактического отправителя массовых сообщений. Текущая кнопка «Рассылка» экспортирует список, но не отправляет кампанию.

## Целевая модель данных

### Базовые сущности PostgreSQL

| Таблица | Ключевые поля | Зачем |
|---|---|---|
| `customers` | `id`, имя, created/updated, `is_internal` | единая карточка человека без дублирования по каналам |
| `customer_identities` | `customer_id`, тип (`telegram`, `email`, `phone`, `zenclass`), нормализованное значение, verified_at | склейка только по подтверждённому идентификатору |
| `consent_log` | `customer_id`, канал, назначение, значение, время, версия текста, источник, Telegram update/message ID, IP для web-формы | доказуемое согласие и отзыв; записи не перезаписываются |
| `products` | код, название, категория, открывает ли VIP | единый каталог для аналитики |
| `orders` / `payments` | источник, внешний ID, товар, сумма/валюта, статусы, paid_at, refund_at | статус VIP-клиента, выручка, возвраты и RFM |
| `access_grants` | клиент, продукт, granted/revoked, reason, source | доступ в боте отдельно от покупки |
| `course_enrollments` | клиент, курс, статус, даты, источник | воронка обучения |
| `event_log` | событие, клиент, время, канал, объект, JSON-свойства | продуктовая аналитика и воронки |
| `campaigns` | канал, шаблон, правило сегмента, создатель, статус, план/факт | управление рассылкой |
| `campaign_recipients` | кампания, клиент, снимок сегмента, status, sent_at, error, tracking | воспроизводимый журнал доставки |

В `event_log` не хранить полные тексты личных сообщений и чувствительные описания. Для inbox достаточно категории, короткого технического фрагмента и срока хранения; оригинал — только если он реально нужен для ответа пользователю.

### Первые события для аналитики

События должны иметь `event_id`, `occurred_at` (UTC), `customer_id`/Telegram ID, `source`, `session_or_campaign_id`, версию бота и безопасные свойства. Первой очередью:

1. `bot_started`, `policy_accepted`, `marketing_opted_in`, `marketing_opted_out`, `bot_blocked`;
2. `section_opened`, `card_received`, `crystal_received`, `dice_rolled`, `angel_requested`, `weather_requested`, `moon_opened`;
3. `store_opened`, `course_opened`, `service_opened`, `contact_opened` — c `utm_campaign` и product/course ID;
4. `vip_code_redeemed`, `vip_access_granted`, `vip_access_revoked`, `vip_content_opened`, `vip_pdf_sent`;
5. `checkout_started`, `order_paid`, `order_refunded`, `course_enrolled` — только из подтверждённого платёжного/учебного источника;
6. `campaign_sent`, `campaign_delivery_failed`, `campaign_clicked`, `campaign_unsubscribed`.

Не нужно собирать «на всякий случай» дату рождения, адрес, пол, медицинские/эзотерические запросы, содержимое переписки или точную локацию. Локация для погоды остаётся краткоживущей функцией и не участвует в сегментации без отдельной понятной цели и согласия.

## Сегменты

Каждый сегмент хранится как именованное правило SQL/API, а перед рассылкой превращается в неизменяемый список получателей — snapshot. Базовый набор:

| Сегмент | Условие |
|---|---|
| `vip_customers` | есть хотя бы один `paid` заказ продукта с `opens_vip = true`, без полного возврата |
| `vip_access_only` | VIP-доступ есть, но подтверждённой покупки нет; контроль ручных выдач |
| `non_vip_leads` | нет оплаченной VIP-покупки |
| `marketing_tg_ready` | согласие `telegram/marketing = true`, бот не blocked, нет глобального стоп-листа |
| `vip_marketing_tg_ready` | пересечение `vip_customers` и `marketing_tg_ready` |
| `warm_non_vip` | не VIP, активность ≤30 дней, есть маркетинговое согласие |
| `sleeping_opted_in` | нет активности >30 дней, согласие есть |
| `new_opted_in` | первый визит ≤7 дней, согласие есть |
| `course_students` | активное зачисление на конкретный курс |

Для каждого сегмента в интерфейсе показывать количество, правила и 20 обезличенных примеров/ID только администратору. Нельзя отправлять «всем VIP» без дополнительной проверки права на маркетинговую коммуникацию.

**Сейчас в боте:** кнопка «VIP» в `/god → Списки` экспортирует пользователей с `vip = true` (VIP-доступ), без различения покупки и ручной выдачи. После миграции сегменты `vip_customers` и `vip_access_only` заменят этот единый список.

## Как управлять рассылками

Рабочий путь вместо ручной правки файлов:

```text
Черновик кампании
  → выбор сохранённого сегмента и превью количества
  → сохранение snapshot получателей
  → тест на внутреннем аккаунте
  → подтверждение администратора
  → отправка малыми пачками
  → журнал sent / failed / blocked / opt-out
  → отчёт по кампании и обновление доступности получателя
```

В Telegram каждая маркетинговая отправка содержит кнопку «Не получать рассылки». Она сразу создаёт `consent_log` с отказом и исключает человека из следующих пачек. Сервисные сообщения (выданный доступ, чек/статус заказа, ответ на запрос) маркируются отдельно и не попадают в маркетинговую кампанию.

На первом этапе это можно открыть в `/god`: «Кампании → Создать → сегмент → тест → подтвердить». Отправитель должен ограничивать частоту, быть идемпотентным по `(campaign_id, customer_id)`, обрабатывать Telegram `Forbidden` как блокировку и продолжать после рестарта с того же журнала. CSV остаётся только контролируемым экспортом, не источником управления.

Для email-рассылок нужен отдельный провайдер транзакционных/маркетинговых писем с обработкой отписок, bounce и complaint. Twenty сам рекомендует для последовательностей и newsletter подключать специализированный маркетинговый инструмент, а не массово отправлять из личного ящика: [документация Twenty](https://docs.twenty.com/user-guide/calendar-emails/how-tos/can-i-send-emails-from-twenty).

## Архитектура

```text
Telegram bot / сайт / оплата / школа
              │ webhooks, API, UTM
              ▼
 PostgreSQL Maranius (источник правды)
     ├─ данные клиентов, согласия, заказы, доступы
     ├─ события и отчёты
     └─ журнал кампаний
              │
      n8n (очереди, расписания, идемпотентные sync)
          ├──────────────► Twenty CRM (карточки, сделки, задачи)
          ├──────────────► Telegram bot (маркетинговые пачки)
          └──────────────► email-провайдер (после выбора)
```

**PostgreSQL** — единственное место, где рассчитываются VIP, согласия и получатели. У бота — отдельная роль БД с минимальными правами; у n8n — другая роль; прямой доступ Twenty к этой БД не давать.

**n8n** — не хранилище клиентов. Его задача: принять webhook, проверить подпись и внешний ID, записать/обновить факт через API, поставить задачу кампании и синхронизировать поле в CRM. Для каждой интеграции обязательны retry, dead-letter журнал и ключ идемпотентности.

**Twenty** — рекомендуется как дополнительное рабочее место для ручной работы: карточка человека, сделки, задачи, заметки, ручные теги и воронка продаж. Он поддерживает API, webhooks и входящие workflow-webhook, поэтому n8n может безопасно синхронизировать ограниченный набор полей; подпись исходящих webhook должна проверяться. См. [webhooks Twenty](https://docs.twenty.com/developers/extend/webhooks) и [входящие workflow-webhook](https://docs.twenty.com/user-guide/workflows/how-tos/connect-to-other-tools/set-up-a-webhook-trigger).

## Решение по Twenty

**Устанавливать имеет смысл, но вторым этапом и в отдельном Docker Compose.** Не переносить в него сырые события бота, VIP-коды, полные логи или единственную копию согласий/заказов. Для Maranius в Twenty достаточно объектов `Person`, `Opportunity` и пользовательских полей: `customer_id`, Telegram ID, статус клиента, VIP-покупатель, последняя активность, маркетинговый статус, source и LTV. Все поля синхронизируются из PostgreSQL в одну сторону, кроме явно разрешённых менеджерских заметок/задач.

Self-hosted Twenty требует собственные PostgreSQL, Redis и persistent storage; официальная compose-конфигурация описывает эти тома и необходимость бэкапа. Размещать его следует на отдельном поддомене и в отдельной сети/проекте, не смешивая с существующей БД инфраструктуры. Релизы закреплять на конкретной версии и обновлять только после резервной копии и проверки на стенде. См. [официальную инструкцию self-host](https://docs.twenty.com/developers/self-host/capabilities/docker-compose).

Не устанавливать Twenty ради самой рассылки: для Telegram кампании эффективнее нативный отправитель Maranius + очередь n8n; для email — специализированный сервис. Twenty останется CRM-интерфейсом и триггером сценариев, а не точкой отказа базы.

## Надёжное хранение и восстановление

### Состояние на 2026-08-26

На production `94.241.142.242` бот healthy. Файлы пользователей лежат в `/opt/apps/maranius/.runtime`, а активность и профиль платформы — в `/opt/apps/maranius/data`. JSON записывается атомарно, рядом сохраняется до 10 валидных копий, а деплой Maranius делает архив данных перед заменой контейнера.

Однако ежедневный `/opt/infra/scripts/backup.sh` сейчас создаёт локальные копии инфраструктуры и PostgreSQL, но не включает `/opt/apps/maranius/.runtime` и `/opt/apps/maranius/data`. Следовательно, текущие JSON защищены от повреждения файла и от неуспешного деплоя, но не от потери сервера между деплоями. Это нужно устранить до начала регулярных рассылок.

### Целевая политика 3-2-1

1. Перевести mutable-данные Maranius в PostgreSQL; JSON оставить только как одноразовый источник миграции/кэш.
2. Ежедневный полный `pg_dump` и постоянное архивирование WAL для point-in-time restore; для JSON на переходный период — согласованный архив `.runtime` и `data` после остановки записи или файловый snapshot.
3. Хранить минимум три копии: рабочая БД, локальный backup на сервере, зашифрованная off-site копия в отдельном Object Storage/аккаунте. Для граждан РФ первичную БД и основной backup размещать в РФ; трансграничную передачу не включать без отдельной правовой проверки.
4. Ретенция: 30 дневных, 12 месячных; доступ к backup только у отдельного технического пользователя, секреты и ключ шифрования не лежат в одном месте с копией.
5. Раз в месяц — автоматическая проверка расшифровки и восстановление в изолированный тестовый PostgreSQL с отчётом: дата последнего успешно проверенного restore, RPO и RTO.

Официальная документация Twenty также рекомендует ежедневные дампы, off-site хранение, шифрование и регулярную проверку восстановления: [backup best practices](https://docs.twenty.com/developers/self-host/capabilities/docker-compose).

## Защита персональных данных и согласия

Текущий opt-in — хорошее начало, но для доказуемой рассылки нужно дописать журнал согласий: кто, когда, каким действием, на какой канал и на какую версию текста согласился или отозвал согласие. Предварительное согласие адресата на рекламу по сетям электросвязи и обязанность прекратить её по требованию закреплены в [статье 18 Закона о рекламе](https://www.consultant.ru/document/cons_doc_LAW_58968/f892dec1383709792452f18d36e7043306e2be0a/). Это проектное требование, а окончательные тексты политики, согласия и вопрос трансграничной передачи нужно проверить у профильного юриста.

Минимальные меры доступа: TLS, закрытая PostgreSQL-сеть без публичного порта, отдельные учётные записи и права, `.env` с правами `600`, секреты вне Git, аудит административных действий, шифрование off-site копий. Права пользователя: отписаться от маркетинга мгновенно, запросить корректировку/удаление в пределах применимых обязанностей хранения, не получать сообщения после блокировки.
