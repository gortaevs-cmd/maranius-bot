# Исправления технического аудита Maranius

Дата: 2026-10-17. Исходная версия: `74dfbb33492080de11f1de12837c942877ff5850`.
Первый блок подготовлен в ветке `codex/audit-block-1`. Production пока не обновлялся.

## Блок 1 — доступ, очередь сообщений и резервное копирование

Подготовлено:

- VIP-callback, включая старые кнопки, проверяет ручную блокировку и обе актуальные
  версии обязательных документов перед проверкой VIP.
- VIP-материалы, ввод кода и административные операции доступны только в личном
  чате. Административный режим ввода не переносится из личного чата в группу.
- `my_chat_member` обновляет существующий профиль владельца личного чата, а не
  профиль самого бота. Служебное событие не создаёт новый профиль до согласий.
- При удалении webhook и запуске polling накопленные updates сохраняются.
- VIP-редактор больше не передаёт `protect_content` в неподдерживающий его
  `edit_text`; защита сохраняется на исходном сообщении и при новой отправке.
- Backup включает существующий `.runtime` и `data`; перед первой миграцией —
  старые `users.json` и `admins.json`. Отсутствие необязательных старых файлов не
  мешает копированию. Ошибка архивации или отсутствие обязательного файла
  останавливают деплой. Неполная копия не подменяет предыдущую проверенную.
- Ошибка до начала замены контейнера не вызывает его перезапуск через rollback.
- Runtime-каталоги и журналы дополнительно исключены из Docker build context.
- Тесты запускаются во временной копии без локальных секретов и рабочих данных;
  сетевые подключения запрещены. CI использует тот же запуск.

Проверка: 119 тестов успешно прошли локально на существующем Python 3.9.6.
Проверен синтаксис shell-скриптов. Docker, shellcheck и Python 3.12 локально
отсутствуют; контейнерная сборка, dependency audit и среда Python 3.12 остаются
проверками GitHub Actions. Отдельный lint/typecheck в проекте пока не настроен.

## Перед публикацией

1. Проверить diff и исходный SHA отката. Изменения не требуют миграции JSON.
2. Через штатное администрирование инфраструктуры установить проверенную версию
   `infra/deploy-maranius-bot.sh` в root-owned
   `/opt/infra/scripts/deploy-maranius-bot.sh`, сохранив предыдущую версию.
   Важно: контейнерная публикация сама не обновляет этот серверный скрипт.
   Ограниченному deploy-аккаунту не предоставлять права его изменения.
3. После команды владельца на публикацию использовать цепочку
   `Tests → Publish verified container → Deploy verified container`.
   Прямой ручной деплой приложения отключён.

## После публикации блока 1

- Убедиться, что опубликован нужный SHA; проверить контейнер, polling и журнал
  без раскрытия токенов и пользовательских сообщений.
- Проверить личные `/start`, VIP и `/god`; обычного пользователя и пользователя
  с ручной блокировкой. Старые VIP-кнопки не должны обходить ограничения.
- Проверить запрет административного CSV и VIP-материалов в группе. Групповые
  уведомления о вступлениях и реакциях должны продолжить работать.
- На отдельном согласованном тестовом пользователе проверить block/unblock и
  изменение `bot_status`. Не изменять согласия реальных пользователей ради теста.
- Проверить состав нового backup: `.runtime/users.json`, `.runtime/admins.json`,
  остальные существующие runtime-файлы и `data`. Архив хранить с ограниченными
  правами; не выгружать его содержимое в общие журналы.
- Проверку сообщений, пришедших за время остановки, проводить на согласованном
  окне обслуживания или отдельном боте; не перезапускать production только ради
  этой проверки. Автотесты уже проверяют сохранение очереди в обоих местах запуска.
- Подтвердить следующий штатный heartbeat в 10:00 МСК.

## Следующие блоки

1. Надёжность уведомлений: достоверный результат доставки Inbox, повторы, безопасные
   журналы без полного update и токенов.
2. Локальные дефекты: кэш погоды при смене места, сохранение даты отзыва VIP,
   продолжение исходного запроса после согласий, календарные периоды отчётов,
   безопасный экспорт пользовательских значений в CSV.
3. Архитектура: отдельный административный handler, затем погода и отчёты.
   Перенос кода и изменение поведения выпускать отдельными коммитами.
4. Хранение и нагрузка: длительные отправки, синхронные JSON-операции, восстановление
   незавершённых связанных записей, пределы памяти и качества healthcheck.
5. До включения рефералов: ключ идемпотентности списания наград и дополнительные
   проверки повторных запросов. Механика остаётся отключённой.

Откат образа не откатывает пользовательские JSON. При необходимости восстановления
данных требуется отдельная согласованная операция, а не автоматическая подмена
всех файлов предыдущей копией.
